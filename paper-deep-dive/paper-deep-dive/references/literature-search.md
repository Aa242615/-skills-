## 为什么这部分最容易翻车

引用关系是 LLM 幻觉的重灾区，原因很实在：论文标题长得都差不多，作者名会重复，年份往往记不准。模型因此经常产出一个**格式完美、扣题准确、但根本不存在**的引用，而且这种错误用户一眼看不出来——他也没读过那篇。

所以这一节的所有规则都围绕一件事：**让每条引用都能被独立核验**。

## 检索源优先级

按"能拿到确切引用关系"的能力排序：

1. **Semantic Scholar Academic Graph API**（免费，无需 key 即可低频调用）
   - 拿论文的 `paperId`：`GET https://api.semanticscholar.org/graph/v1/paper/DOI:<doi>?fields=title,year,venue,authors,abstract,citationCount,referenceCount,externalIds`
   - **前驱**（本文引用的）：`GET .../paper/<id>/references?fields=title,year,venue,authors,externalIds,abstract&limit=100`
   - **后续**（引用了本文的）：`GET .../paper/<id>/citations?fields=title,year,venue,authors,externalIds,contexts,intents&limit=100`
   - `contexts` 字段会返回**引用它的那篇论文里提到它的原句**——这是判断"后续工作是真的用了它还是在 related work 里凑数"的关键，务必取用。
2. **OpenAlex API**（完全免费，无 key，限流宽松）
   - `https://api.openalex.org/works?filter=doi:<doi>` 拿 `id`，再用 `cited_by_api_url` 拿所有引用它的工作。
   - 覆盖面比 Semantic Scholar 更广，适合补后者漏掉的引用。
3. **Crossref API**（免费）——校验 DOI 与期刊/会议名是否准确，作为最后一道核对。
4. **arXiv API**（免费）——`http://export.arxiv.org/api/query?search_query=id:<arxiv_id>` 拿预印本信息与最新版本日期（判断"发表年份"时要注意 arXiv v1 和正式发表年份的差异）。
5. **WebSearch / WebFetch**——用于补充任意来源都覆盖不到的近期工作，以及抓取作者主页/项目页。

调用 API 时用 `curl` 或 Python `requests` 都可以；注意加 `User-Agent`，Semantic Scholar 无 key 时限流约为 1 请求/秒，批量请求之间要 `sleep(1)`。

## 三个方向的检索方法

**方向一：本文引用了哪些别人的工作（前驱）**
不要只列参考文献表——那可能有 60 条，用户看不过来。做法是在前驱里**找出真正构成本文基础的那 5–8 条**：通常在 Related Work 和 Method 里被反复提到、或者被拿来做基线的。每条说明"本文从它那里拿走了什么"。

**方向二：谁发展了本文（后续）**
这一步要用 `citations` 接口，然后按 `contexts` 里的原句筛选——**真正用了本文方法的** 和 **仅在 related work 里提一句的**，价值完全不同，必须分开列。优先展示：
- 直接改进了本文方法的工作；
- 把本文方法用到新领域的工作；
- 复现并质疑本文结论的工作（这类最有汇报价值）；
- 综述文章。

**方向三：同期的竞争工作**
同一时间段、解决同一问题但路线不同的工作。汇报时导师很可能会说"那 XX 那篇呢"，有准备就不会被问住。

## Undermind / 付费工具的替代

Undermind 是付费的深度文献检索服务，没有 API 供程序调用。如果用户有账号并要求使用：

1. **让用户自己跑**：把整理好的检索式交给用户，请他把结果（标题 + 链接 + 摘要）贴回来，由你整理排版。不要假装自己能访问。
2. 同时**并行用 Semantic Scholar / OpenAlex 做一轮**，作为交叉验证——即便用了 Undermind，也应至少用免费源核对一遍关键引用的真实性。
3. 如果用户坚持要自动化，说明代价：需要他自己申请 key 或走浏览器自动化，并且仍然绕不开人工核验。

**不要把"用了 Undermind"当成严谨性的证明。** 严谨性来自每条引用都能被点开验证。

## 防幻觉规则

1. 每条引用**必须有** DOI 或 arXiv ID 或官方页面 URL，三者之一。
2. 写进产物前，**逐条实际访问过一次**（WebFetch 或 API 返回）。API 返回的字段直接引用，不要凭记忆写标题年份。
3. 拿不准的措辞降级：把"该工作证明了 X"改成 API/摘要里支持的表述。引用别人的结论时，如果只看了摘要，就说明"（据摘要）"。
4. **宁可少写**。检索到的有效后续只有 2 条，就写 2 条并注明"该文较新，后续工作尚少"。用户会信任一份诚实的两条列表，而不会原谅一份编造的五条列表。
5. 明确区分三种关系：**直接改进** / **应用到他处** / **仅被提及**。混为一谈会误导用户对本文影响力的判断。
6. 检索完全失败时（例如论文太新、太冷门），如实写"未检索到公开的引用记录"，并建议用户去 Google Scholar 手动查。

## 产物 D 模板

```markdown
# 相关工作与引用脉络

## 一、本文引用了什么（前驱）
### 1.1 构成本文基础的核心工作
### 1.2 被用作基线的对比方法
（每条：题名 / 作者 / 年份 / 会议 / 链接 / **本文从它那里拿走了什么**）

## 二、谁发展使用了本文（后续）
（先写检索日期与检索源，例如"检索于 2026-09-19，Semantic Scholar + OpenAlex"。）
### 2.1 直接改进本文的工作
（每条：题名 / 年份 / 链接 / **它具体改了什么** / 引用语境原句）
### 2.2 应用到其他领域的工作
### 2.3 复现或质疑本文的工作
### 2.4 综述中的定位

## 三、同期的竞争路线
## 四、脉络小结
（一句话说明这篇论文在这条研究线上的位置：它接过了谁的棒，又把棒传给了谁？）
```
