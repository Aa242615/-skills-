## 产物 A《论文精读》

目标读者：**用户本人**，用来在汇报前把论文吃透、并应对导师追问。

```markdown
# <论文中文译名> — 论文精读

> 原标题：<English Title>
> 作者：<全部作者>　单位：<主要单位>
> 发表：<会议/期刊全称 年份>　DOI/arXiv：<链接>

## 一句话概括
（用一句没有任何术语的话说明这篇论文干了什么。检验标准：讲给非本专业的人听，他能复述出来。）

## 1. 工作背景：为什么会有这篇论文
### 1.1 这个问题从哪来
（这条研究线是怎么走到今天这一步的。把它当作一个故事讲：早先人们怎么做，遇到了什么麻烦，于是有人提出了什么，又带来了什么新麻烦，最后轮到本文。）
### 1.2 前人做法的具体缺陷
（要具体到能复现的程度。例如"需要逐像素标注，标注成本约 X 人时/千张"，而不是"效率低"。）
### 1.3 本文想做的事
（本文的目标 + 它自己声明的边界，也就是作者明说不打算解决的问题。）

## 2. 方法：它是怎么做的
### 2.1 整体流程
（文字 + 一张流程复述图。图用 Mermaid 或文字箭头，不要直接截图原文图，PPT 里才用原文图。）
### 2.2 关键模块逐个拆解
（每个模块三行：它接收什么、做什么、输出什么。公式用 LaTeX 写，并且逐个符号解释——汇报时台下最常卡住的就是符号。）
### 2.3 训练 / 推理细节
（数据从哪来、怎么标注、超参、算力开销。这些是"可复现性"问题，导师常问。）

## 3. 成果：它做到了什么
### 3.1 主实验
（表格复述：数据集 / 对比基线 / 指标 / 本文数值 / 提升幅度。每个数字标注表号。）
### 3.2 消融与补充实验
（哪一部分贡献最大、哪一部分其实可有可无——这往往是论文最有信息量、又最少被汇报的部分。）
### 3.3 论文自己承认的局限
（原文 Limitations / Discussion 说了什么；作者没说的也要补一句「本文未讨论」。）

## 4. 我的评价
### 4.1 真正的贡献是什么（你的判断，标注「推断」）
### 4.2 可疑之处
### 4.3 如果导师问这三个问题，怎么答
（预判三个最可能被追问的问题并给答案。这是本产物最实用的一节。）
```

**质量检验**：读完第 1 节，一个外行应该能明白"为什么这值得研究"；读完第 2 节，一个同行应该能画出方法框图。

## 产物 B《技术与术语》

目标读者：**用户 + 听众**。用户拿它准备答疑，听众拿它当术语卡。

```markdown
# 技术与术语

## 一、论文用到的关键技术
按重要性排序，每项固定四段式：

### 1. <英文术语>（中文译名）
- **是什么**：两句话讲清，不用更多。
- **论文里怎么用的**：具体到哪个模块、完成什么功能、和原版比做了什么改动。这一条最重要——很多汇报只讲"这个技术是什么"，不讲"作者拿它干嘛"。
- **为什么用它而不是别的**：作者的选型理由（引原文表达）。
- **如果被问到**：一句话补刀，通常是它的缺点或替代方案。

## 二、名词解析表
| 英文 | 中文 | 一句话解释 | 首次出现位置 |
|---|---|---|---|
（覆盖正文所有专业名词，包括数据集名、指标名、架构名。）

## 三、背景知识补充
（听众不具备但理解本文必需的前置知识，每个不超过 5 行。例如本文基于 Transformer，而听众可能只懂 CNN。）
```

**反面示例**：把"Transformer 是一种基于自注意力的网络架构，由 Vaswani 等人于 2017 年提出"写完就结束——这是在写教科书，不是在做汇报准备。必须落到"本文怎么用它"。

## 产物 E《可延伸的 Idea》

目标读者：**用户本人**，用来在汇报末尾给出"我的思考"，或者在导师问"你接下来想做什么"时接得住。

默认**合并为一个 `.md`**。用户明确要求"每个 idea 一份文档"时，才按 `idea-01-<slug>.docx` 拆分。

每个 idea 固定结构：

```markdown
## Idea 1：<一句话标题>
**来源**：论文第 X 节指出 / 我观察到图 Y 中……
**现在没人做**：（为什么这还是个空白。要具体，例如"现有工作都在单模态上验证，跨模态未见报道"。）
**具体怎么做**：3–5 步，可执行到"下周就能开工"的程度。
**预期收益与风险**：（以及最小验证实验怎么设计——先做一个什么实验就知道这条路通不通。）
**需要的资源**：数据 / 算力 / 代码 baseline。
**相关文献**：（支撑这个想法的已有工作，附链接。）
```

生成 idea 的顺序建议（从易到难，先保证有 3 条扎实的）：

1. **补论文的遗留问题**——作者在 Limitations 里自己承认的。
2. **换设定**——换数据集 / 换模态 / 换规模 / 换评测指标，看结论还成不成立。
3. **方法拼接**——把本文模块和另一条技术线结合。
4. **质疑假设**——论文某处默认成立的前提，如果去掉会怎样。这类 idea 最有价值也最难，通常来自复现失败或消融异常。
5. **应用落地**——用在本领域的实际问题上。

每条 idea 都要回答"**为什么现在做是时机**"：是算力够了、数据开源了，还是新方法刚出现使得它变得可行。答不上来的想法大概率别人早试过了。
